## はじめに

社内向けの業務システムで、管理画面のデザインガイドラインを作りました。同じ業務をスマホでも PC でも行うシステムで、画面の実装は主に AI エージェントが行っています。この記事では、ガイドラインの考え方と作り方を紹介します。

## 背景と課題

UI/UX の判断は、主観に寄りやすいと感じていました。UI/UX には「これが正解」と言い切れる場面が少なく、好みや印象で決まりやすいからです。専門家が同じ画面を評価しても、判断はなかなか揃わないことが知られています[^evaluator]。

主観で決めていると、プロダクト全体で見たときに、同じ場面なのに画面ごとに見せ方や振る舞いが違う、ということが起きやすくなります。共通の基準がないと、同じ問題に対して別々の解決策が生まれることは NN/g も指摘しています[^consistency]。ばらつきは利用者の負担にもなります。同じものが画面ごとに違うと「同じことなのか、別のことなのか」を毎回考えることになり、ボタンの位置が変われば押し間違いも起きます。

さらに、主観で決めたものは「なぜそうしたのか」を説明できず、あとから見直す手がかりも残りません。そのため、同じ議論が何度も繰り返されます。

そこで、ガイドラインを作るときに次の 3 つを大事にしました。

1. **社内システムであることを前提にする**。考えることと考えないことを分ける
2. **なぜその案にしたのかを残す**。DDR（Design Decision Records）の考え方を取り入れる
3. **ガイドライン作りから実装まで、AI で回す**。AI が読んで従えるだけでなく、ガイドラインを作るところも AI と一緒に進める

ここからは、この 3 つをどうガイドラインに落とし込んだかを順に紹介します。

## 社内システムのデザインで考えること・考えないこと

社内システムは、利用者も使い方も決まっています。誰がどの端末でどれくらい使うかがわかり、利用者に直接話も聞けます。そこで、一般向けのサービスの物差しをそのまま当てはめず、利用実態をもとに考えることと考えないことを分けました。

- **考えること**: 毎日の業務を早く正確に終えられること。誤った操作を手前で防ぐ、端末が変わっても手順を変えない、同じものは同じ言葉で呼ぶ、など
- **考えないこと**: 今の利用者に使う場面がないもの。ダークモードや読み上げソフト向けの対応などは、求められてから足す

考えないことも、理由つきで書いておきます。そうすれば「なぜ対応していないのか」に答えられ、求められたときにはその理由をもとに決め直せます。

## 決めた理由を残す: DDR の考え方を脚注に組み込む

### DDR とは

決めた理由を残す方法として、DDR（Design Decision Records）という考え方があります。ADR（Architecture Decision Records）と同じ形で、UX・インタラクション・見た目などのデザインの決定を、背景・決定・検討した案・影響と一緒に 1 件ずつ残すものです。技術の決定は ADR、プロダクトの振る舞いは PDR、デザインは DDR と分けて残す考え方もあります[^ddr]。

### 記録を分けず、ガイドラインの脚注に組み込む

今回は DDR の考え方を取り入れつつ、記録を別に作らず、**ガイドラインの脚注に組み込む**形にしました。

- 本文のルールには「今どうするか」だけを書く
- 脚注には、その判断の記録を書く。理由のないルールは書かない
- いつ何をどう変えたかは git の履歴に任せ、文書には「以前は〜だった」と書かない

記録を分けなかったのは、人も AI も、今の決まりとその理由を一度に読めるようにするためです。決定の記録が別にあると、どれが今も有効なのかをたどる手間がかかり、ガイドラインと記録が食い違うおそれもあります。

### 脚注が答える 4 つの問い

脚注には、次の問いのうち中身があるものに答えます。

- **何で決めたか**: 後で説明する根拠の順番のどれで決めたか
- **何を諦めたか**: 選んだ案の弱み
- **何を選ばなかったか**: 比べて選ばなかった案
- **どうなったら決め直すか**: 見直すきっかけ

決め直すときに、どの根拠が崩れたら変えられるか、どの弱みが表に出たら見直すかを読めるようにするのがねらいです。DDR の「背景・決定・検討した案・影響」は、ほぼそのまま脚注に入っています。ステータスや置き換えの履歴は持たない代わりに、見直すきっかけを最初から書いておきます。

たとえば、フォームのパターンには次のように書いています（一部を簡略化しています）。

```text
- フォームにキャンセル・戻るのボタンを置かない[^4]

[^4]: 主操作を「保存」1 つに絞り、押し間違いと「キャンセルすると保存されるのか」という迷いを生まない。
戻り方はブラウザとナビゲーションが常に担っている。複数の画面にまたがる入力に戻るリンクを必ず置く資料
（GOV.UK）や、キャンセルを求める資料（NN/g）もある。ここは 1 画面で完結し、ブラウザの戻るとサイドバーで
出口が足りる業務の事実で決めている。複数の画面にまたがる入力を作るときは、この判断を見直す
```

本文は 1 行だけで、4 つの問いの答えは脚注で読めます。

- 何で決めたか: 1 画面で完結するという業務の事実
- 何を諦めたか: GOV.UK や NN/g のすすめには従わない
- 何を選ばなかったか: 戻るリンクとキャンセルボタン
- どうなったら決め直すか: 複数の画面にまたがる入力を作るとき

### 根拠の順番を決める

「何で決めたか」を揃えるために、根拠の順番を決めています。

1. 客観的な根拠（外部の一次資料、利用実態や業務の事実、利用者の声）
2. 既存のパターン・既存の画面
3. 使っている UI ライブラリの既定
4. 主観（好み、印象、「他のサービスで見かけた」）

候補を並べてそれぞれの根拠の強さを比べ、一番上のものを選びます。1 案ずつ検討すると、先に見つけた案が根拠の弱いまま残ってしまうためです。主観の案は、ライブラリの既定を上書きするような独自実装が要るなら選びません。

資料どうしで意見が割れる、根拠があるのに従わない、実装の都合で決める、といった場合は、選ばなかった案も必ず書きます。根拠がないまま決めたときは、何で決めたか（既存に揃えた、ライブラリの既定、主観など）を書き、根拠が見つかったら決め直します。

### 判断を保留にしない

判断は、選ぶか選ばないかのどちらかで決めます。保留にすると置き場がなく、ガイドラインの外に散らばって、同じ案が何度も検討し直されるためです。見直したい判断は、いったん決めたうえで、脚注に見直すきっかけを書きます。

## 根拠にする一次資料

「客観的な根拠」として当たる一次資料も決めています。

| 種類                               | 資料                                                                                                                             |
| ---------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| 規格                               | WCAG 2.2                                                                                                                         |
| 実装の事実                         | HTML の仕様、MDN、ブラウザや OS の実際の動き                                                                                     |
| プラットフォームの公式ガイドライン | Apple Human Interface Guidelines、Material Design 3                                                                              |
| デザインシステム                   | デジタル庁デザインシステム、SmartHR Design System、GOV.UK Design System、Carbon Design System、Atlassian Design System、Fluent 2 |
| 調査に基づく記事                   | Nielsen Norman Group（NN/g）、Baymard Institute                                                                                  |

資料ごとに重みも決めていて、規格と実装の事実が強、公式ガイドライン・デザインシステム・調査記事が中です。

使い分けとしては、「なぜそうするのか」の理由は NN/g、守るべき最低ラインは WCAG、同じ場面で実際にどう決めているかは他社や行政のデザインシステム、という形になることが多いです。業務システムに近い SmartHR やデジタル庁、Carbon、Atlassian は特に参考になります。

当たり方のルールは 2 つです。

- **ルールを書く前に調べる**。書いたあとに出典を探すと、自分の結論に合う資料だけを拾ってしまう
- **URL が実在し、当てはまる記述があることを確かめてから載せる**。AI に調べさせるときは特に大事

なお、社内システムでは一次資料のない「利用実態・業務の事情」も根拠になります。その場合は出典がないぶん、どの事実から決めたかを脚注に書きます。

## ガイドラインの構成

ガイドラインは `docs/design/` に置いていて、次の 2 つでできています。

- `README.md`: 共通原則、パターン一覧、根拠の順番、パターンの書き方、保守のルール
- `patterns/*.md`: ボタン、エラー、確認、一覧、空のデータなど、場面ごとのパターン（20 個以上）

パターンは「場面 → 判断 → 理由」の形で、1 ファイル 1 パターンで書きます。見せ方の判断はデザインガイドライン、コードの書き方は別の開発ガイドライン、と役割を分けています。

## パターンを AI と作るスキル

ここまでの決まりを、AI が手順どおりに回せるようにしたのが、Claude Code のスキル `design-guidelines-pattern` です。当てはまるパターンがない UI を作るときや、実装の途中で迷ったときに使います。

### 判断は人、調べるのは AI

スキルで一番大事にしているのは役割の分け方です。

- 判断はすべて人が下す。AI は調べて、論点ごとにおすすめを出し、人が決めるまで書かない
- 聞くのは 1 問ずつ。事実は AI が調べて済ませ、人には判断だけを聞く

### 資料のそろい方で決め方を変える

AI は論点ごとに、次のどの型にあたるかを考えます。

| 型  | 場面                                   | 進め方                     | 脚注に書くこと           |
| --- | -------------------------------------- | -------------------------- | ------------------------ |
| A   | 資料が揃っていて、業務の事実とも合う   | そのまま選ぶ。人は確認だけ | 理由と出典               |
| B   | 資料が割れている、または資料に従わない | 人が決める                 | 選ばなかった側とその理由 |
| C   | 資料がなく、業務の事実だけで決める     | 人が決める                 | どの事実から決めたか     |

型 A にしたくなる論点ほど、資料の割れ方を先に書き出してから型を決めるようにしています。AI が楽な結論に流れないようにするためです。

### 進め方

スキルは 6 つのステップで進み、それぞれに完了の条件を決めています。AI が途中のステップを飛ばさないようにするためです。

1. **題材と論点を仮置きする**: 既存画面のコードから実例を集め、調査ファイルを作る
2. **一次資料に当たる**: 決めた資料のすべてに当たり、何と言っているかを引用と URL で残す。書いていなければ「無し」と書く
3. **論点を 1 つずつ決める**: どの型にあたるか・選択肢・おすすめを添えて人に聞く。決まったら、ルールの 1 行と脚注の文面を見せて確認を取る
4. **書く**: パターンの型どおりに書き、関連するパターンや一覧も直す
5. **実装との食い違いを並べる**: ルールを 1 行ずつコードと突き合わせ、1 件ずつ「チケットにする」か「今のままにする」かを人に聞く
6. **終える**: 人が OK を出したら終わり

細かいところでは、次のような工夫をしています。

- 資料に書いていないことも「無し」と残す。調べ漏れなのか、本当に書いていないのかを区別できる
- 人が「再提案しない」と言った案も脚注に入れる。AI が同じ案を何度も出してこないようにする
- 目の前の実装に合わせてルールをゆるめない。ゆるめるなら根拠の順番で決め直し、その理由を脚注に残す

## ガイドラインに沿って AI に実装させる

実装では、AI エージェント向けの AGENTS.md から、UI を作る・変えるときにデザインガイドラインを開かせています。

```markdown
2. デザインガイドライン: docs/design/README.md（UI を作る・変えるときに開く。見せ方の判断指針。コードの書き方は開発ガイドライン）
```

ガイドラインの README には「UI を作る・変えるときは、当てはまるパターンを必ず読んでから着手する」と書いています。当てはまるパターンがなければ、前の章のスキルでパターンを作ってから実装に進みます。UI の見え方を変えるときは、当てはまるパターンも同じ PR で直すルールです。

## やってみてどうだったか

よかったのは、根拠をもとに話せるようになったことです。「どちらが好きか」ではなく「どの根拠で決めるか」で話せるので、レビューで好みの議論が減りました。UI/UX を考えるときに迷うことも減りました。

一方で、1 つのパターンを決めるのには時間がかかります。資料どうしで意見が割れて、なかなか決めきれないこともあります。

これから同じことをやるなら、最初は共通原則と根拠の順番だけ決めればいいと思います。完璧を目指さず、迷った場面から 1 つずつパターンにしていけば十分です。

## まとめ

- 社内システムでは、考えることだけでなく、考えないことも理由つきで決める
- 主観は最後に使い、何で決めたか・何を諦めたか・何を選ばなかったか・どうなったら決め直すかを脚注に残す
- 判断は人が下し、調べる・書く・実装するのは AI に任せる
